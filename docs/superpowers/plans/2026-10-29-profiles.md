# Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Switchable profiles on one device (issue #117). Each profile has its own SQLite file. Apple Health, Health Connect and the Watch are owner-only.

**Architecture:**
- **Files.** The owner keeps `ischys.db`, which doubles as the device database: it holds the `profiles` registry and the device settings. Each other profile gets `ischys-<id>.db`.
- **Switching.** The exported `db` becomes a switchable facade, so the 14 repo modules don't change. A switch swaps the connection, runs registered reset hooks, and remounts the tab navigator.
- **Health and Watch.** Every Health and Watch path checks one gate, `isOwnerActive()`.

**Tech Stack:** Expo / React Native, expo-router, Drizzle + expo-sqlite, expo-secure-store, `node --test` for pure logic, SwiftUI (watchOS, ActivityKit), Kotlin / Compose (Wear OS).

**Spec:** `docs/superpowers/specs/2026-10-29-profiles-design.md`. **UI source of truth:** `design-handoff/design_handoff_profiles/README.md` and `Profiles.dc.html` (board 16a). Executors read the spec, the handoff README and this plan. Where they disagree, the spec's "Corrections to the handoff" section wins.

## Global Constraints

- **Existing data:** the owner's file stays `ischys.db` and its existing SecureStore key names stay unchanged. Nothing is moved or rewritten.
- **Non-owner keys:** non-owner SecureStore keys are `ischys.p.<profileId>.<original key>`.
- **Settings scope:**
  - Per profile: unit, effort mode, auto-start rest timer, weekly goal, bodyweight, bar & plates (kg and lb), deload advice, count warm-ups, name, initials.
  - Device-wide: appearance, theme, haptics, rest-timer alerts, Health connection, chart range, exercise demo media, Live Activity hint.
- **Health and Watch** (Apple Watch and Wear OS) are owner-only. Non-owner profiles have no toggles, no Health reads or writes, and no Watch session.
- **Copy:**
  - No pronouns for the owner. Use "‹Owner›'s …".
  - When the owner's name is still `DEFAULT_NAME` ("Athlete"), use "the phone's owner".
  - No competitor names.
- **Tokens:** only existing tokens (`src/theme/tokens.ts`). Light and dark mode both. Accent tints through `accentA()`.
- **Transactions:** `db.transaction` callbacks stay synchronous, and `atomically` bodies await only database statements (`src/db/client.ts`).
- **One profile changes nothing:** with a single profile, nothing changes except the Settings PROFILE section (P1b). Export file names stay `ischys-export.<fmt>`.
- **Flag:** everything reachable sits behind `PROFILES_ENABLED`. It stays `false` until Task 15.
- **Commits:** no `Co-Authored-By` or AI attribution lines in commit messages (owner rule).
- **Checks:** `npm test` and `npm run typecheck` (from `frontend/`) pass at the end of every task.

## Review Focus

1. **Stale state after a switch.** A module-level cache (unit, effort mode, summary cache, exercise picker…) serves or writes the previous profile's data. Expected: nothing from profile A is visible or written after switching to B. Pinned by the source-scan test in Task 6.
2. **Relaunch with a workout running in a profile that isn't the last-used one** (for example after a Live Activity background launch). Expected: the app opens in the workout's profile. Pinned by the `resolveLaunchProfile` tests in Task 1.
3. **A registry id with no row** (deleted profile, interrupted delete). Expected: the app falls back to the owner and never crashes on launch. Pinned in Task 1 (`resolveLaunchProfile`) and Task 12 (delete order).
4. **A Watch or Wear message arriving while a non-owner is active** (a stale Start screen tapped, or heart-rate notes). Expected: ignored, and nothing written to the owner's Health or to the client's workouts. Pinned by the source-scan test in Task 7.
5. **Names in other scripts, emoji and single words.** For example "Μαρία Παπαδάκη", "Ζωή", "  ", "🏋️ Nik". Expected: sensible initials and slug, and no empty export stem. Pinned in Task 1.

### Task 2: Switchable database connection

**Files:**
- Create: `frontend/src/db/switchable.ts`, `frontend/src/db/switchable.test.ts`
- Modify: `frontend/src/db/client.ts`

**Interfaces:**
- Consumes: none.
- Produces:
  - `createSwitchable<T extends object>(initial: T): { handle: T; swap(next: T): void; current(): T }` in `switchable.ts`. A `Proxy` whose `get` reads from the current target, and binds functions to that target.
  - In `client.ts`:
    - `deviceDb: Db`, always the `ischys.db` connection.
    - `db: Db`, the facade. Same type as today.
    - `type ProfileConnection = { id: string; fileName: string; expo: SQLiteDatabase; drizzle: Db; atomic: ReturnType<typeof createAtomic> }`
    - `fileNameFor(profileId: string): string`, giving `'ischys.db'` for the owner and `` `ischys-${id}.db` `` otherwise.
    - `openConnection(profileId: string): ProfileConnection`: opens the file, sets `PRAGMA foreign_keys = ON`, and doesn't migrate.
    - `useConnection(conn: ProfileConnection): void`: swaps `db`, `atomically` and `transactionOpen` to `conn`.
    - `currentConnection(): ProfileConnection`
    - `closeConnection(conn: ProfileConnection): void`: a no-op for the owner.
  - `atomically` and `transactionOpen` keep their signatures and act on the current connection.
  - `useDbReady` stays for now and runs on the owner connection. Task 3 removes it.
