# Localization (zh-Hans first) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The phone app shows its UI, built-in exercise / muscle / category / equipment names and dates in Simplified Chinese when the system language is Chinese, with per-string English fallback, translations generated by a DeepSeek script and safety-checked by Claude.

**Architecture:** A tiny dependency-free translator (`src/i18n/`) keyed by string ID, with English source strings carrying context notes and a generated `zh-Hans.json`. Catalog names are display labels looked up by stable ID at the data layer's read-for-UI boundary; storage, sync, export and import keep English. A Node script calls DeepSeek for new/changed strings, tracks English hashes and review status per key, and writes a review file Claude checks.

**Tech Stack:** Expo SDK 57 / React Native, TypeScript, drizzle + expo-sqlite, `expo-localization` (new, only new dependency), `node --test`, DeepSeek chat-completions API (OpenAI-compatible, `https://api.deepseek.com/chat/completions`, model `deepseek-chat`; verify against DeepSeek's current docs before Task 7).

**Spec:** `docs/superpowers/specs/2026-11-05-localization-design.md`

## Global Constraints

- Read the Expo v57 docs (https://docs.expo.dev/versions/v57.0.0/) before touching `expo-localization` or `app.json` (`frontend/AGENTS.md`).
- Languages: `en` (source) and `zh-Hans` only. Traditional Chinese → English.
- No schema change, no migration. Database, sync, backup JSON, CSV export/import keep English names exactly as today.
- Custom exercises (`isCustom = 1`) always show the stored name. Renamed built-ins (stored name ≠ catalog English) show the stored name.
- How-to steps stay English. Watch / Wear / widget / Live Activity / notification fixed labels stay English; they receive the translated exercise name as data.
- Glossary values are fixed (spec table): 组, 次, 动作, 训练, 训练计划, 热身组, 递减组, 力竭组, 超级组, 个人纪录 (纪 not 记); RPE / 1RM / PR / kg / lb / Ischys untranslated.
- `DEEPSEEK_API_KEY` from env only (`source ~/.zshrc` first in a non-interactive shell). Never print, log, commit or echo it.
- A string flagged by the safety check never ships in Chinese.
- No competitor app names anywhere in code, comments, prompts or docs.
- Commits: owner's identity, no `Co-Authored-By` / AI attribution lines (owner's standing rule).
- Tests: `cd frontend && npm test` and `npm run typecheck` must pass after every task.

## Review Focus

1. **Editing a built-in's name on a Chinese phone** — a field prefilled with the Chinese label and saved unchanged must not write Chinese into the DB (which would turn it into a "renamed" exercise forever). Test in Task 3.
2. **Backup / CSV from a Chinese phone** — must be byte-identical to the same data exported on English. Test in Task 3.
3. **Searching on a Chinese phone with English or pinyin-less Latin input**, and searching custom exercises with Chinese names — both must match. Test in Task 2.
4. **A zh string with a broken or missing placeholder / plural form** — must fall back to English, never render `{count}` literally. Tests in Tasks 1 and 7.
5. **Locale tags** `zh-Hant-TW`, `zh-HK`, `zh-MO` → English; `zh-SG`, `zh-CN`, `zh-Hans-CN`, bare `zh` → zh-Hans; `en-GR` → English. Test in Task 1.

### Task 7: Translation script

**Files:**
- Create: `frontend/scripts/i18n/core.mjs` (pure), `frontend/scripts/i18n/translate.mjs` (CLI), `frontend/scripts/i18n/glossary.zh-Hans.json`, `frontend/src/i18n/zh-Hans.state.json`
- Test: `frontend/scripts/i18n/core.test.js`

**Interfaces:**
- Consumes: `strings` (Task 1/5/6 `en.ts`; read via a small export step or by transpiling — implementer's choice), catalog source (Task 2 `catalogSource.mjs`).
- Produces:
  - State file: `Record<key, { enHash: string; status: 'pending'|'ok'|'flagged'|'manual'; reason?: string }>`, keys namespaced `ui:<key>`, `ex:<id>`, `mu:<id>`, `cat:<id>`, `grp:<name>`, `eq:<value>`, `plist:<key>`.
  - `core.mjs`: `hashEn(s): string`; `needsTranslation(key, en, state, opts:{retryFlagged:boolean}): boolean` (new key, or enHash changed and status ≠ manual-with-same-hash; flagged only with retryFlagged); `buildPrompt(batch, glossary): {system: string, user: string}`; `parseResponse(text, batch): {ok: Record<key,string>, rejected: Record<key,string>}` (rejects placeholder mismatch, empty, Latin-only output for non-glossary strings, length > 2× en for fixed-width notes).
  - CLI: `node scripts/i18n/translate.mjs --lang zh-Hans [--dry-run] [--retry-flagged] [--batch 60]` → writes results into `zh-Hans.json` / catalog `zh-Hans.json` / `locales/zh-Hans.json`, marks them `pending`, and writes `scratch review file` `frontend/.i18n-review/zh-Hans.review.json` (gitignored) listing `{key, en, zh, note}` for every pending item. `node scripts/i18n/translate.mjs --apply-review <file>` reads `{key, status:'ok'|'flagged', reason}` entries: `ok` → state ok; `flagged` → remove the zh value (English fallback) and record the reason.
  - Strings marked `manual` (hand fixes from issue feedback) are never overwritten while their enHash matches.
- Prompt rules (exact intent): Simplified Chinese for mainland China; plain, neutral, standard gym terminology; no idioms, jokes, slang, political or cultural references; keep `{placeholders}` and glossary-untranslated terms verbatim; respect max length in notes; return JSON `{key: translation}` only. Use `response_format: {type:'json_object'}`, `temperature: 0`.
- Key handling: read `process.env.DEEPSEEK_API_KEY`; if missing, exit with "DEEPSEEK_API_KEY not set" — never print any part of it; never include it in error output (strip headers from logged errors).
